[#eventing]
= Eventing

====
Note: The eventing concept defined in this chapter is *experimental*.
Normative clauses may change in future versions of this specification without a deprecation period.
Sections marked as _(informative)_ are not normative.
====

[#eventing-introduction]
== Introduction and Relevance

The interfaces defined in this specification follow a request/response pattern.
A client that needs to know whether Asset Administration Shells, Submodels, or Concept Descriptions have changed has to ask for it, e.g. by periodically calling
xref:specification/interfaces.adoc#GetAllSubmodels[GetAllSubmodels] or the recent-changes operations such as
xref:specification/interfaces.adoc#GetAllSubmodelsRecentChanges[GetAllSubmodelsRecentChanges].
Polling scales poorly with the number of objects and clients, detects changes only with a delay, cannot observe deletions, and does not tell the client _which part_ of a Submodel has changed.

Many use cases, however, depend on reacting to changes in time: a customer has to be informed about a product change notification of a supplier, a replica or search index has to follow its source, or an application has to react when a measured value changes.
Eventing addresses these use cases.
An AAS service publishes an _event_ for every change of its model content, and interested consumers receive or retrieve these events.

This chapter defines

* the event model, i.e. the CloudEvents context attributes and the data of an event (Clause <<eventing-event-model>>),
* the event types and the trigger points that produce them (Clauses <<eventing-event-types>> and <<eventing-trigger-points>>),
* event profiles for domain-specific events (Clause <<eventing-profiles>>),
* transport-independent delivery requirements and the HTTP Event Feed as a pull-based delivery channel (Clause <<eventing-delivery>>).

An event consists of three parts: the _trigger_ (the committed change that caused it), the _context_ (the CloudEvents attributes that describe what happened where and when), and the _data_ (the payload describing the changed object).
How an event is transported (HTTP, MQTT, Kafka, AMQP, ...) and how the transport is secured are aspects of the _notification_ and are not part of the event itself.
This chapter defines the event and the HTTP Event Feed; broker bindings are described in an informative way only.
<<fig-eventing-overview>> illustrates this separation.

[#eventing-related-concepts]
=== Relation to other Concepts (informative)

*Recent changes.* The operations `GetAll...RecentChanges` return identifiables created or changed after a given point in time.
They are suited for an initial or periodic synchronization.
Events complement them: they also report deletions and changes of individual SubmodelElements, and they are delivered as soon as the change has been committed.

*History.* The operations
xref:specification/interfaces.adoc#GetAssetAdministrationShellVersionByIdAndDate[GetAssetAdministrationShellVersionByIdAndDate] and
xref:specification/interfaces.adoc#GetSubmodelVersionByIdAndDate[GetSubmodelVersionByIdAndDate]
return the state of an identifiable at a given point in time.
A consumer that receives an event without the changed content (see Clause <<eventing-presentations>>) can use them with the `time` of the event to retrieve exactly the state the event describes.

*EventElements of the metamodel.* Part 1 xref:bibliography.adoc#bib1[[1\]] defines the experimental classes
link:{mm}/spec-metamodel/submodel-elements.html#EventElement[EventElement],
link:{mm}/spec-metamodel/submodel-elements.html#BasicEventElement[BasicEventElement], and
link:{mm}/spec-metamodel/submodel-elements.html#EventPayload[EventPayload].
These classes describe events that are declared as part of the model content of a reactive Asset Administration Shell and are bound to a source EventElement.
The events defined in this chapter are different: they are produced by the AAS services for every change of the model content, independent of whether the model contains EventElements.
They neither require nor use the classes above.

[#eventing-use-cases]
== Use Cases (informative)

[#eventing-use-case-pcn]
=== Product Change Notification

A supplier maintains a Submodel with Product Change Notifications (PCN) for its products, e.g. an announced discontinuation or a changed material.
Each new notification is added as a new record to the Submodel.
Customers who purchased the product need to learn about the new record without polling the Submodels of all their suppliers.
With eventing, the supplier's repository publishes a domain-specific event that contains the new record (see Clause <<eventing-profile-pcn>>).
The customer subscribes to exactly this event type, restricted to the _globalAssetIds_ of the parts it purchased, and can start its internal processes, e.g. a requalification, directly from the event.

[#eventing-use-case-synchronization]
=== Synchronization, Caching and Indexing

Replicas, caches, search indexes, registry synchronization jobs, and dataspace connectors need to follow the content of a repository.
They consume all events of a repository and apply the state carried in the events.
Because events carry the state after the change (or the last state before a deletion), a consumer can apply them idempotently and does not need to know the previous state.

[#eventing-use-case-monitoring]
=== Monitoring of Operational Data

Applications observe individual values, e.g. a temperature in a Submodel with operational data.
They filter SubmodelElement events by the _semanticId_ of the element or of the containing Submodel and by _globalAssetId_, and receive the new value with the event.

[#eventing-use-case-onboarding]
=== Asset Onboarding and Twin Discovery

A customer receives a physical asset and wants to learn when the Asset Administration Shell for this asset becomes available, or when the assignment of an Asset Administration Shell to an asset changes.
Asset events (see Clause <<eventing-asset-events>>) report exactly these changes of the link between an asset and its Asset Administration Shells.

[#eventing-use-case-downstream]
=== Downstream Processes

Changes of specific Submodels trigger follow-up processes, e.g. republishing a digital product passport when one of its content Submodels changes, or updating a compliance report when a certificate Submodel changes.
Such processes filter Submodel events by the _semanticId_ of the Submodel.

[#eventing-approach]
== Technologies and Approach

[#eventing-cloudevents]
=== CloudEvents

Events are represented as CloudEvents xref:bibliography.adoc#bib16[[16\]] in the JSON event format xref:bibliography.adoc#bib17[[17\]].
CloudEvents is a vendor-neutral specification for describing event data in a common way.
It defines a small set of context attributes, a type system, and protocol bindings for HTTP, MQTT, Kafka, AMQP, and further transports xref:bibliography.adoc#bib18[[18\]].
Using CloudEvents allows the same event to be delivered through different channels without changing its content, and it allows consumers to use existing CloudEvents tooling.

[#eventing-design-principles]
=== Design Principles

The event model is based on the following principles:

. *CloudEvents core attributes only.* An event shall be fully described by the CloudEvents core context attributes listed in Clause <<eventing-context-attributes>>.
This specification does not define CloudEvents extension attributes.
. *No new models for model content.* The data of an event shall be composed of representations that already exist in the AAS metamodel xref:bibliography.adoc#bib1[[1\]] and in this specification, in particular the xref:specification/interfaces-operation-parameters.adoc#SerializationModifier[SerializationModifiers].
The event data classes of this chapter only group these representations.
. *State, not deltas.* The data describes the state of the object after the change, or its last state before a deletion.
Consumers can apply events idempotently and without knowledge of the previous state.
. *Committed changes only.* Events shall only be produced for changes that have been successfully and durably applied.
. *Transport independence.* The content of an event does not depend on the delivery channel.
. *Two presentations.* Each event is available in a _Regular_ presentation that contains the changed content and a _Compact_ presentation that only references it (Clause <<eventing-presentations>>).

[#eventing-source-subject]
=== Source and Subject

The `source` of an event is the URI-reference of the collection resource that contains the changed object.
The `subject` is the identification of the changed object within this collection.
For AAS, Submodel, SubmodelElement, and Concept Description events, appending "/" and the encoded subject to the source yields the URL of the changed object in the HTTP/REST API.
Identifiers are encoded with base64url and idShortPaths are URL-encoded, as defined in Clause xref:http-rest-api/http-rest-api.adoc#design-decisions[Design Decisions].
The `subject` itself shall not be encoded.

.Source and subject
[%autowidth,width="100%",cols="16%,34%,25%,25%",options="header",]
|===
|Events of |source |subject |Resource URL
e|AssetAdministrationShell |`\{base}/shells` |link:{mm}/spec-metamodel/datatypes.html#Identifier[Identifier] of the AAS |`\{base}/shells/\{aasIdentifier}`
e|Submodel |`\{base}/submodels` |Identifier of the Submodel |`\{base}/submodels/\{submodelIdentifier}`
e|SubmodelElement |`\{base}/submodels/\{submodelIdentifier}/submodel-elements` |link:{mm}/mappings/mappings.html#_format_path_idshortpath_serialization_in_json[idShortPath] of the SubmodelElement |`\{base}/submodels/\{submodelIdentifier}/submodel-elements/\{idShortPath}`
e|ConceptDescription |`\{base}/concept-descriptions` |Identifier of the Concept Description |`\{base}/concept-descriptions/\{cdIdentifier}`
e|Asset |`\{base}/lookup/shells` |link:{mm}/spec-metamodel/core.html#globalAssetId[globalAssetId] |see Clause <<eventing-asset-events>>
|===

`\{base}` is the base URL of the HTTP/REST API of the event producer, including any path prefix, as it is used by clients.
A producer without an HTTP/REST API shall use an absolute URI that identifies the service instance instead.

The source of an object is independent of the path that was used to change it.
For example, a Submodel changed via the superpath `/shells/\{aasIdentifier}/submodels/\{submodelIdentifier}` of an AAS Repository still uses the source `\{base}/submodels`.

====
Note: Asset events are the only exception to the URL rule, because an asset is not a resource of the HTTP/REST API.
The Asset Administration Shells of an asset are retrieved with
xref:specification/interfaces.adoc#GetAllAssetAdministrationShellIdsByAssetLink[GetAllAssetAdministrationShellIdsByAssetLink].
====

[#eventing-event-types]
=== Event Types

Event types follow the pattern

....
io.admin-shell.<resource>.<change>.v<major>
....

where `<resource>` is one of `aas`, `submodel`, `submodelelement`, `conceptdescription`, or `asset`, `<change>` is one of `created`, `updated`, or `deleted`, and `<major>` is the major version of the event contract.
The major version shall be incremented for changes of the event data that are not backward compatible.

[#eventing-presentations]
=== Presentations

The data of every event is defined in two presentations:

* *Regular* contains the state of the changed object.
For _deleted_ events, it contains the last state before the deletion.
* *Compact* contains a link:{mm}/spec-metamodel/referencing.html#Reference[Reference] to the changed object instead of its state.

Attributes that describe the context of the changed object, i.e. `globalAssetIds` and the `submodel` Reference of SubmodelElement events, are contained in both presentations.
The following table defines the representation of the object in each presentation by means of the xref:specification/interfaces-operation-parameters.adoc#SerializationModifier[SerializationModifiers].

.Representation of the changed object per presentation
[%autowidth,width="100%",cols="28%,24%,24%,24%",options="header",]
|===
|Data class |Attribute |Regular |Compact
e|AssetAdministrationShellEventData |`assetAdministrationShell` |AssetAdministrationShell; Content _Normal_ |Reference; Content _Reference_
e|SubmodelEventData |`submodel` |Submodel; Content _Metadata_ |Reference; Content _Reference_
e|SubmodelElementEventData |`submodelElement` |SubmodelElement; Content _Normal_, Level _Deep_, Extent _WithoutBLOBValue_ |Reference; Content _Reference_
e|ConceptDescriptionEventData |`conceptDescription` |ConceptDescription; Content _Normal_ |Reference; Content _Reference_
e|AssetEventData |`assetAdministrationShells` |References to the linked AAS |omitted
|===

The Regular presentation of Submodel events uses the Content _Metadata_, i.e. it does not contain the SubmodelElements.
Changes of SubmodelElements are reported by SubmodelElement events; repeating the complete Submodel in every Submodel event would duplicate them and would not be bounded in size.

Every Reference that a producer creates for an event, i.e. the Reference of the Compact presentation and the `submodel` Reference of SubmodelElement events, shall contain the attribute `referredSemanticId` if the referenced object has a _semanticId_.
References that are part of the serialized model content, e.g. the `submodels` of an Asset Administration Shell, are serialized as stored.
Event data shall be serialized according to the JSON serialization of Part 1 xref:bibliography.adoc#bib1[[1\]]; in particular, empty lists shall be omitted.

A consumer shall determine the presentation of a received event from its `dataschema`, because a producer may deliver the Compact presentation instead of the Regular one (Clause <<eventing-size-limits>>).

[#eventing-global-asset-ids]
==== Determination of globalAssetIds

The `globalAssetIds` of Submodel, SubmodelElement, and profile events shall contain the _globalAssetId_ of every Asset Administration Shell that is known to the producer and references the Submodel at the time of the change.
An Asset Administration Shell is known to the producer if it is managed by the same service or by a service whose content the producer can read consistently at the time of the change.
The list is a snapshot: if an Asset Administration Shell adds or removes a reference to the Submodel later, no Submodel event is produced; the change is reported by an `io.admin-shell.aas.updated.v1` event instead.

====
Note: consequently, a Submodel Repository that does not have access to Asset Administration Shells provides no `globalAssetIds`.
Consumers that maintain an index from assets to Submodels should build it from AAS events.
====

A producer may define a maximum number of entries.
If the number of Asset Administration Shells exceeds this maximum, the producer shall omit the attribute `globalAssetIds` for the affected event, and shall document this behavior.

[#eventing-trigger-points]
== Trigger Points

[#eventing-trigger-general]
=== General Rules

The following rules apply to all event types:

. An event shall be produced if and only if the persisted model content of the producer was changed successfully.
Operations that fail, are rejected, or are rolled back shall not produce events.
. An operation that does not change the persisted state, e.g. a replacement with identical content, shall not produce events.
. Events are determined by the change of state, not by the operation that caused it.
The same change shall produce the same events regardless of whether it was caused by a repository operation, an operation via a superpath, an import of an AASX package or an environment, or an internal process of the service.
. One change may produce several events.
All of them shall have the same `time`.
. A change of a Submodel shall produce exactly one `io.admin-shell.submodel.*` event.
If SubmodelElements were changed, the SubmodelElement events (Clause <<eventing-sme-events>>) shall precede the Submodel event of the same change.
. If an identifiable is created or deleted, no SubmodelElement events shall be produced for its content.
. A change of an Asset Administration Shell shall produce exactly one `io.admin-shell.aas.*` event.
Asset events (Clause <<eventing-asset-events>>) caused by the same change shall follow it.

[#eventing-sme-events]
=== Derivation of SubmodelElement Events

SubmodelElement events shall be derived by comparing the state of the Submodel before and after the change, regardless of the operation that caused the change.
The following rules apply:

. For every changed attribute, the affected element is the innermost SubmodelElement that contains the attribute.
Child elements, i.e. elements in `value` of SubmodelElementCollections and SubmodelElementLists, in `statements` of Entities, and in `annotations` of AnnotatedRelationshipElements, are elements of their own and are not attributes of their parent.
. An affected element that existed before and after the change shall produce one `submodelelement.updated` event.
. An added element shall produce one `submodelelement.created` event and a removed element one `submodelelement.deleted` event.
No events shall be produced for the child elements of an added or removed element.
. A parent element shall not produce an event only because one of its child elements changed.
. A change of the `idShort` of an element shall be reported as `submodelelement.deleted` for the previous idShortPath and `submodelelement.created` for the new idShortPath.
. The index of an element in a SubmodelElementList is part of its idShortPath.
If a change moves existing elements of a list to other indexes (insertion or removal that is not at the end of the list, or reordering), one `submodelelement.updated` event shall be produced for the list instead of events for the individual moved, added, or removed elements.
Appending elements to the end of a list and removing elements from the end of a list produce `submodelelement.created` and `submodelelement.deleted` events for these elements.
. Events for several affected elements of the same change shall be ordered by the position of the elements in the Submodel (depth-first, in document order).
. A producer may define a maximum number of SubmodelElement events per change.
If a change exceeds this maximum, the producer shall produce no SubmodelElement events for this change; the `submodel.updated` event is produced as usual.
The producer shall document this maximum.

.Examples for the derivation of SubmodelElement events
[%autowidth,width="100%",cols="45%,55%",options="header",]
|===
|Change |SubmodelElement events
|Value of `Measurements.temperature` changed |`updated` for `Measurements.temperature`
|`description` of `Measurements` and value of `Measurements.temperature` changed |`updated` for `Measurements`, `updated` for `Measurements.temperature`
|Collection `Maintenance` with two Properties added |`created` for `Maintenance`
|Property `Measurements.pressure` removed |`deleted` for `Measurements.pressure`
|`idShort` of `Measurements.temp` changed to `temperature` |`deleted` for `Measurements.temp`, `created` for `Measurements.temperature`
|Element appended to list `Records` with three elements |`created` for `Records[3]`
|Element inserted at index 0 of list `Records` |`updated` for `Records`
|Value of `Records[1].Title` changed |`updated` for `Records[1].Title`

[#eventing-asset-events]
=== Derivation of Asset Events

Asset events report changes of the _link_ between an asset, identified by its link:{mm}/spec-metamodel/core.html#globalAssetId[globalAssetId], and the Asset Administration Shells known to the producer.
An Asset Administration Shell is linked to an asset if the attribute `globalAssetId` of its link:{mm}/spec-metamodel/core.html#AssetInformation[AssetInformation] has this value or, for a discovery service, if an xref:specification/interfaces-payload.adoc#AssetLink[AssetLink] with the name `globalAssetId` and this value is registered for it.

.Link states of an asset
[[fig-eventing-asset-link-states]]
[plantuml, eventing-asset-link-states, svg]
....

....

The following rules apply:

. `asset.created` shall be produced when the first Asset Administration Shell is linked to an asset.
. `asset.updated` shall be produced when the set of Asset Administration Shells linked to an asset changes and remains non-empty.
. `asset.deleted` shall be produced when the last Asset Administration Shell is unlinked from an asset.
. A change of an Asset Administration Shell that does not change its link shall not produce asset events.
. If the _globalAssetId_ of an Asset Administration Shell changes from `A` to `B`, events for both assets shall be produced: for `A` either `asset.updated` or `asset.deleted`, and for `B` either `asset.created` or `asset.updated`.
. The producer shall serialize the determination of asset events per _globalAssetId_, so that concurrent changes produce exactly one `asset.created` and exactly one `asset.deleted` event per transition.

|AAS with _globalAssetId_ `X` created; another AAS is linked to `X` |`asset.updated` for `X`
|AAS changed without changing its _globalAssetId_ |none
|_globalAssetId_ changed from `A` to `B` |`asset.updated` or `asset.deleted` for `A`; `asset.created` or `asset.updated` for `B`
|AAS with _globalAssetId_ `X` deleted |`asset.updated` or `asset.deleted` for `X`
|===

[#eventing-profiles]
== Event Profiles

The generic event types report every change of the model content.
For some domains, a dedicated event type is more convenient: it has a domain-specific meaning, can be subscribed to directly, and can carry exactly the relevant content.
An _event profile_ defines such event types on top of the generic ones.
Event profiles are typically defined together with a Submodel template.

An event profile shall define

. the event types, following the naming pattern of Clause <<eventing-event-types>> with a resource name specific to the profile; profiles that are not defined by the IDTA shall use a reverse-DNS prefix of the defining organization instead of `io.admin-shell`,
. the trigger condition as a condition on the changes derived according to Clause <<eventing-sme-events>>, usually restricted to Submodels with a specific _semanticId_,
. `source` and `subject` according to Clause <<eventing-source-subject>>,
. the event data for both presentations, composed of the representations defined in the AAS metamodel and this specification,
. the data schema identifiers.

Profile events shall be produced in addition to the generic events of the same change and shall precede the `submodel.*` event of this change.
All requirements of Clause <<eventing-delivery>> apply to profile events; their ordering key is the identifier of the Submodel.

[#eventing-delivery]
== Delivery

[#eventing-delivery-general]
=== General Requirements

. Events shall be delivered at least once.
Consumers shall detect duplicates by the combination of `source` and `id`.
. An event that has been produced for a committed change shall not be lost, even if the producer or a delivery channel fails temporarily.
. The content of an event shall not change after it has been produced.
Within one delivery channel, a repeated delivery of an event shall be identical to the first one.

====
Note: a common way to fulfill the first two requirements is to store the event in the same transaction as the model change and to deliver it afterwards (transactional outbox).
====

[#eventing-ordering]
=== Ordering

Events with the same ordering key shall be delivered in the order of the changes that produced them and, for one change, in the order defined in Clause <<eventing-trigger-general>>.
No order is defined between events with different ordering keys.

.Ordering keys
[%autowidth,width="100%",cols="50%,50%",options="header",]
|===
|Event types |Ordering key
|`io.admin-shell.aas.*` |Identifier of the AAS
|`io.admin-shell.submodel.*`, `io.admin-shell.submodelelement.*`, profile events |Identifier of the Submodel
|`io.admin-shell.conceptdescription.*` |Identifier of the Concept Description
|`io.admin-shell.asset.*` |globalAssetId
|===

The `time` of an event shall not be used to order events, because changes committed in parallel may become visible in a different order than their timestamps.

[#eventing-size-limits]
=== Size Limits and Presentation Fallback

Delivery channels may limit the size of an event.
A producer may define a maximum event size per delivery channel.
If an event in the Regular presentation exceeds this maximum, the producer shall deliver the event in the Compact presentation through this channel.
The fallback event shall have the same `id`, `source`, `subject`, `type`, and `time`, and the `dataschema` of the Compact presentation.
The decision shall be made once per event and delivery channel and shall not change on repeated delivery.

A consumer that receives a Compact event can retrieve the state it describes with
xref:specification/interfaces.adoc#GetSubmodelVersionByIdAndDate[GetSubmodelVersionByIdAndDate] or
xref:specification/interfaces.adoc#GetAssetAdministrationShellVersionByIdAndDate[GetAssetAdministrationShellVersionByIdAndDate] and the `time` of the event, or the current state with the corresponding Get operation.

====
Note: splitting an event into several messages or replacing it with events for child elements is not permitted, because it would change the meaning of the event and the number of events for the same change.
====

[#eventing-event-feed]
=== HTTP Event Feed

The HTTP Event Feed is a pull-based delivery channel.
A consumer retrieves the events of a service page by page, optionally restricted by filters.
Reading events does not remove them from the feed.

[#eventing-event-feed-operation]
==== Operation GetAllEvents

.GetAllEvents
[%autowidth,width="100%",cols="20%,10%,70%",options="header",]
|===
|Operation |Verb |Path
|GetAllEvents |GET |`/events`
|===

The response is a Result object as defined in Clause xref:http-rest-api/http-rest-api.adoc#pagination[Pagination], whose `result` contains the events in the JSON event format of CloudEvents and whose `paging_metadata` contains the cursor for the next page.

.Parameters of GetAllEvents
[%autowidth,width="100%",cols="18%,27%,55%",options="header",]
|===
|Parameter |Values |Explanation
e|type |event types, comma-separated |Returns events of one of the given types.
e|id |base64url-encoded Identifiers, comma-separated a|Returns events whose object is or belongs to one of the given identifiables:

e|semanticId |base64url-encoded, JSON-serialized References, comma-separated |Returns Submodel and SubmodelElement events whose changed object has one of the given References as _semanticId_ or _supplementalSemanticId_.

The following semantics apply:

. All parameters are optional.
Different parameters are combined with a logical AND; the comma-separated values of one parameter are combined with a logical OR.
. Filters are evaluated on the event as produced, independent of the requested presentation.
. Two References are equal if they have the same `type` and the same list of keys with equal `type` and `value`.
. The feed returns events in a server-defined publication order that is consistent with Clause <<eventing-ordering>>.
The order shall not change between requests.
. `lastEventId` and `since` shall not be combined.
If `lastEventId` refers to an event that is unknown or no longer retained, the server shall respond with the status code _ClientErrorResourceNotFound_.
. If a cursor is given, the filters and the presentation of the request that returned the cursor apply.
Filters and presentation given together with a cursor shall be equal to them; otherwise, the server shall respond with the status code _ClientErrorBadRequest_.
. The server defines how long events are retained and shall document it.
A consumer that missed events beyond the retention period has to read the current state from the respective AAS services.

[#eventing-event-feed-authorization]
==== Authorization

GetAllEvents requires the right READ according to Part 4 xref:bibliography.adoc#bib3[[3\]].
In addition, the server shall return an event only if the caller may read all content of the event:

* the changed object,
* for events with `globalAssetIds`, the Asset Administration Shells from which they were derived,
* for asset events, all Asset Administration Shells referenced in the data and the Asset Administration Shell whose change produced the event.

An event for which these permissions cannot be established shall be omitted as a whole.
The server shall not remove parts of an event.

[#eventing-broker-bindings]
=== Message Broker Bindings (informative)

Events can be delivered through message brokers using the CloudEvents protocol bindings xref:bibliography.adoc#bib18[[18\]].
The following recommendations apply:

* Use the structured content mode with the media type `application/cloudevents+json`, so that the message carries the complete event independent of the broker's header capabilities.
* Use the ordering key of Clause <<eventing-ordering>> as partition or message key where the broker supports it, e.g. as the Kafka record key.
* Use at-least-once delivery, e.g. MQTT quality of service 1 or higher.
* Derive topic or routing key names from the event type.
The structure of topic names is not defined by this specification.
* Configure the maximum event size of Clause <<eventing-size-limits>> below the message size limit of the broker, taking the size of the context attributes into account.

====
Note: message brokers usually grant access per topic and cannot evaluate the rules of Clause <<eventing-event-feed-authorization>> per event.
Every consumer with access to a topic receives the complete events, including the model content of the Regular presentation.
Operators should deliver the Compact presentation through brokers whose access control is not fine-grained enough for the Regular presentation.
====

[#eventing-security-considerations]
== Security Considerations (informative)

* Events of the Regular presentation contain model content.
They shall be protected like the content itself.
* `globalAssetIds` reveal which assets use which Submodels.
The authorization rules of Clause <<eventing-event-feed-authorization>> therefore also cover the Asset Administration Shells from which they were derived.
* Asset events of a _deleted_ or _updated_ type can reveal that an Asset Administration Shell was unlinked from an asset.
* Events do not contain information about the actor who caused the change.
Audit information is outside the scope of events.

[#eventing-query-language]
== Optional Approach: Filtering with the AAS Query Language (informative)

[IMPORTANT]
====
*This clause is a proposal for discussion and is not part of this specification.*
It describes a possible extension of the xref:query-language.adoc[AAS Query Language] for filtering events.
Implementations shall not assume that it will be standardized in this form.
The normative filters of the HTTP Event Feed are the query parameters of Clause <<eventing-event-feed-operation>>.
====

The query parameters of GetAllEvents cover common filters, but they cannot express arbitrary combinations, e.g. an OR across different attributes or a negation.
The AAS Query Language could provide these capabilities with an additional root element `$event` for FieldIdentifiers:

.Possible FieldIdentifiers for events
[%autowidth,width="100%",cols="40%,60%",options="header",]
|===
|FieldIdentifier |Value
|`$event#type` |`type` of the event
|`$event#source` |`source` of the event
|`$event#subject` |`subject` of the event
|`$event#time` |`time` of the event
|`$event#globalAssetIds[]` |entries of `globalAssetIds`
|`$event#semanticId` |_semanticId_ of the changed object, see Clause xref:query-language.adoc#references[References]
|`$event#submodelSemanticId` |_semanticId_ of the Submodel of Submodel, SubmodelElement, and profile events
|===

A query could then be sent to a new operation, e.g. `QueryEvents` with `POST /query/events`, or be used to define subscriptions.
The following query selects all SubmodelElement events of Submodels with a given semanticId, except for one asset:

[source,json]
----
{
  "$condition": {
    "$and": [
      { "$starts-with": [ { "$field": "$event#type" }, { "$strVal": "io.admin-shell.submodelelement." } ] },
      { "$eq": [ { "$field": "$event#submodelSemanticId" }, { "$strVal": "https://example.com/semantics/OperationalData/1/0" } ] },
      { "$not": { "$eq": [ { "$field": "$event#globalAssetIds[]" }, { "$strVal": "https://example.com/ids/asset/0000" } ] } }
    ]
  }
}
----

Standardizing this approach requires changes of the BNF grammar and of the JSON Schema, which are shared with the Access Rules of Part 4 xref:bibliography.adoc#bib3[[3\]] (see Clause xref:query-language.adoc#formula-grammar-sot[Single source of truth for the formula grammar and JSON Schema]).
